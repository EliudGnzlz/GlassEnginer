# LEYES DEL MOTOR — GlassEnginer (fijadas por D3m3tr10, 2026-11-04)

Esto es lo que el usuario quiere en su motor, salido del SDD y de sus propias palabras. Rige TODA orden que se le dé al Harness (o a cualquier IA) sobre este proyecto: ninguna orden puede contradecir estas leyes ni inventar alcances fuera de ellas. Si una tarea parece exigir romper una ley, se consulta primero con el usuario.

## A. Identidad y propósito (palabras del usuario)
1. **MCP nativo desde el inicio.** El motor trae su propio servidor MCP: es la vía principal para trabajarlo con IA directamente. No es un accesorio ni se elimina; crece con el motor.
2. **C# es el respaldo humano.** Scripting embebido (CoreCLR/.NET 8) con API estilo Unity en comportamiento, para que el usuario pueda seguir sus proyectos programando a mano si las IA fallan. Los nombres de la API se pueden renombrar después para diferenciarse y optimizar.
3. **Meta: beta jugable y open source.** La beta debe compilar un juego jugable con gráficos, audio y físicas, y ofrecerse open source para que cualquiera lo use.
4. **Enfoque del motor: generación procedural robusta (aclarado por el usuario).** No es que el motor sea "de roguelites": los roguelite son solo el ejemplo típico porque usan procedural. Lo que se quiere es que el motor pueda crear/borrar/regenerar mundos y salas muchas veces, en segundo plano o en tiempo real, sin saturar memoria ni procesos y sin tirones aunque la sala tenga muchos objetos. Hay un límite físico, pero la meta es empujar cuánto se puede generar y a qué velocidad dentro de ese límite. Pendiente acordado: el usuario pasará su generador de mapas procedural en C# hecho en Unity (muchas iteraciones) para analizarlo y portar EL MISMO generador a GlassEnginer y comparar comportamiento/memoria.
4c. **Shaders: grafo visual PROPIO estilo Shader Graph (DECISIÓN del usuario, 2026-11-04).** Los grafos de nodos de Blender NO se pueden traer a ningún motor (realidad aceptada por el usuario). En su lugar, el motor tendrá SU propio modelo de grafos de shader, inspirado en el de Unity (sin copiarlo tal cual): la gente aprenderá el del motor, pero será el único sistema a aprender. Alcance fijado: empezar por lo básico, como todo el motor — un set mínimo de nodos para la beta (salida PBR, color, valores, textura, tiempo, operaciones simples tipo sumar/multiplicar/mezclar, UV) que compile a los shaders del motor, y crecer después. **Las dos ideas van unidas (precisión del usuario):** habrá además una librería de shaders PREFABRICADOS tipo "brochas" — básicos pero llamativos — y cada prefabricado será un grafo ABIERTO y editable, para que la gente aprenda el sistema modificando shaders que ya funcionan. Primeros prefabricados nombrados por el usuario: **agua, espuma, fragmentos, láser, brisa y tormenta de arena**. Prerrequisito anotado: hoy el cargador glTF ni siquiera importa el material PBR estándar ni las texturas (solo geometría; el color es plano por entidad), así que la importación automática de materiales va primero o junto con esto.
4e. **UI de juego tipo Canvas de Unity (requisito del usuario, 2026-11-04):** el motor debe tener sistema de UI para los videojuegos (Canvas, RectTransform con anclas, texto, imágenes, botones), usable desde C#. Estado verificado: la BASE ya existe en glass_core (CanvasData, RectTransformData, UITextData, UIButtonData en scene.rs; las escenas de prueba traen HUD Canvas + texto de puntaje). No se parte de cero: falta completarlo como sistema de UI de juego pleno y que funcione también en el standalone, no solo dentro del editor.
4d. **Launcher (requisito del usuario, 2026-11-04): hay que rehacerlo.** El actual (glass_editor/src/launcher.rs) no convence al usuario. Dirección fijada: aspecto del **Launcher/Hub VIEJO de Unity, NO el actual**. Y regla de oro: el Launcher es **siempre offline**; internet solo se usa para (a) descargar el motor, (b) actualizaciones, y (c) una **sección de comunidad** donde los usuarios suban sus creaciones (shaders, mapas, juegos, etc.). Nada de exigir conexión para trabajar. **Modelo de distribución confirmado por el usuario:** el Launcher se descarga desde GitHub (Releases) y es el Launcher quien descarga el motor **con los ejemplos** incluidos. Estado verificado: hoy el launcher es un panel dentro del editor y no tiene ni una línea de código de red/descarga; hay que separarlo como app propia y crear ese módulo de descarga/actualización, además de que exista el repo y un paquete de motor publicable.
4b. **Enlace directo con Blender (tipo Godot).** Al modificar y guardar un `.blend`, el motor debe reflejar el cambio automáticamente (vigía de assets → Blender headless → `.glb` → recarga en caliente de la malla). Estado verificado 2026-11-04: el enlace `.blend` SÍ está implementado en el código (watcher.rs + check_asset_reloads); FBX no estaba soportado todavía. **Actualización 2026-11-05 (P2 cerrada): FBX YA está soportado** por la misma vía — el vigía detecta el `.fbx`, el puente headless de Blender lo convierte a `.glb` y la recarga en caliente lo refleja en el motor, sin importador binario propio. Requisito: Blender instalado en la máquina del usuario.

## B. Anti-sobreingeniería (SDD §2)
5. Vulkan con `ash` + `gpu-allocator`. Prohibido escribir un asignador de memoria GPU propio.
6. Grafo Entidad-Componente jerárquico simple, mapeo 1:1 con C#. Nada de frameworks ECS hipercomplejos.
7. Puente C#↔Rust plano: C-ABI, `#[repr(C)]`, punteros opacos/handles. Nada de wrappers de reflexión pesada.
8. Nada de parsear `.blend` nativo: Blender headless en segundo plano → `.glb` → crate `gltf`.
9. MCP ligero: JSON-RPC sobre stdio o HTTP localhost, sin middleware innecesario.

## C. Forma de trabajar (SDD §3 y práctica del usuario)
10. Hitos verificables, en orden: uno cerrado antes de empezar el siguiente. Nada de módulos a medias presentados como completos.
11. Parches quirúrgicos: nunca reescribir un archivo entero por un cambio pequeño.
12. Errores de compilación parseados (archivo/línea/columna exactos), no volcados crudos al modelo.
13. No inventar API de Vulkan: consultar los headers/`ash` antes de usar una función o struct.
14. Validar la alineación FFI Rust↔C# antes de compilar.
15. Toda iteración cierra con tests corriendo y reporte honesto. Prohibido declarar "100% verificado" sin evidencia ejecutada (la lección de PROGRESO.md).

## D. Decisiones fijadas (2026-11-04)
16. **Vulkan 1.3 hasta después de la beta.** La modernización (stack, dynamic rendering, synchronization2) es una iteración dedicada post-beta, no se mezcla con features.
17. **Las escenas de prueba se conservan** (SampleScene, Nivel2): son ejemplos importantes del motor, no se borran.
18. **Nada de `target/` ni artefactos de build** en paquetes ni en GitHub: eso va en `.gitignore`. El proyecto son las fuentes.
19. **El standalone es deuda prioritaria**: la beta no se declara lista sin que `build/standalone` produzca un juego ejecutable (hito 10 del SDD).
